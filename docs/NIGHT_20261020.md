## 今夜わかったこと

1. **書込みが 1 MiB で止まった原因は時計ではなかった。**
   `wr 800,1B4,80018000` = 2 チャンク成功 + 最後の 436 セクタ全滅。マルチ
   ブロック書込みは最後のブロックがホストを離れても終わっておらず、カードは
   DAT0 を握ったまま (CMD/DAT_INHIBIT)。そこへ次の CMD25 を投げたので
   CMD_TIMEOUT、その後の 1 セクタずつのフォールバックが busy なカードを
   引き継いで 436 連敗。10 分はここで消えていた。
   → `wait_idle`（CMD12 後と各データ転送前）、`recover_lines`（SPEC 3.00
   3.3.13 の CMD/DAT ソフトウェアリセット）、連続 8 失敗で打ち切り。

2. **PHY が死んでいた。** `PHY_CTRL1 (0xFF390000+0x430)` は一度も
   パワーオンされておらず、ベンダーの `sdhci_of_arasan_platform_init`
    （EN_RTRIM → DLL_TRIM_ICP=4 → PDB → CALDONE 待ち → EXR_NINST 待ち）を
   移植した。プッシュプル設定は `PHY_CTRL2 = 0x003FF7FC`、駆動強度は基板の
   `drv-strength = <4 4>` に合わせて 40Ω。時計ラダーは PHY 無しでは
   全 rung 失敗（`0x015EFA00`）だったので、これが 25 MHz の前提。

3. **Garble は再列挙せずに直す。** 応答はすべて直前の SETUP から導出される
   ので、`ep0_resync`（TX FIFO 掃引 + STALL 解除 + EP0 再アーム）で十分。
   バスサイクルは「再アームすら拒否されたとき」だけ。

4. **数字の getvar は裸の 16 進で返す。** `OKAY0xC00000` をホストが
   `strtoul(base 16)` で読むと `x` で止まって 0 になり、
   "couldn't parse max-download-size" と「kernel パーティション 0 バイト」
   になっていた。

5. **フラッシュ中の見張りを止めた。** 400 kHz で分単位かかる書込みを
   frozen-boot レーンが「死んだブート」と読んでリセットしていた
   （02:16 の切断がこれ）。`write_sectors` が busy を立て、frozen-boot と
   USB zombie の両レーンがその間だけ黙る。

6. **分割。** `ane_emmc.rs` 2039 → 1236 行（パネル診断 800 行を
   `ane_emmc_diag.rs` へ）、`ane_usb_dev.rs` 2833 → 2254 行（fastboot
   コマンド解釈 576 行を `fastboot_dispatch::poll()` へ、セッション状態
   147 行を `fastboot_session.rs` へ）。残る分割案は `docs/usb-split.md`。

## 03:00–04:00 にやったこと

   （clk_xin 200 MHz で 100 MHz）から始めていた。JESD84-B50 6.6.2 では
   HS_TIMING が default speed のままのカードは 26 MHz までしか規定されて
   いないので、100 MHz は「速い時計」ではなく「死んだバス」で、失敗した
   バスサイクルが線を握ったまま次の rung を全部巻き込んでいた。今は
   12.5 → 16.7 → 20 → 25 MHz の順に登り、最初の失敗で止める。各 rung は
   CMD16（RCA 不要でべき等）でバスに声をかけてから CMD17 を 2 回読み、
   両方が MBR 署名を持ち一致することを要求する（`2c3e1bde`）。
   `getvar emmc` の nibble が rung ごとの結果、bits 32..40 が最初の失敗。

## 朝のランブック（更新）

1. 端末を LK に入れる（電源長押し ~10 秒 → Vol- を押しながら USB）。
2. `python3 cycle_flash.py artifacts/fullerene-ane-v340c-sof.img`
3. `fastboot getvar emmc`:
   - 下位バイト 4 か 5 → 20/25 MHz まで登った（flash は数十倍速くなる）
   - 0 のまま → bits 32..40 の「最初に失敗した field」と nibble を見る
   - 併せて `oem log` の `em: crgb4=` で clk_xin を確認する
4. `fastboot getvar flash` で書込みカウント、`oem log` で `em: c25_*`。
5. `fastboot oem sof` — SOF フレーム数とカウンタ幅が 2 つの 16 進数で出る。
   `span / frames` が 1 ms あたりのカウンタ刻み → ×1000 が本当の CNTFRQ。
   `oem sof restart` で窓を開き直せる。これが `uptime_us` の 10 倍の答え。
6. `fastboot oem hs on` — CMD6 で EXT_CSD[185]=1。戻りが `OKAY01` なら
   カードは高速モードに入り、続けてラダーが 33/50 MHz まで登る。
   `getvar emmc` で chosen が 2 か 3 なら成功。`oem hs off` で戻せる。
7. `fastboot oem i2c4 6B 0 16` / `oem i2c4 25 0 8` をケーブル抜き差しの
   2 回（`docs/charger.md`）。I2C の STOP/RESTART/READ ビットは修正済み
   （`46754a26`）なので、ここで NACK が出れば本当に配線か電源の問題。
8. タッチ: 起動後に `T0`〜`T8` がリングに出る。`T8: iddone` の後に
   `TOUCH:xxxxxxxx` が出れば、20 秒のラダー修正（`46754a26` + `10b5ff1f`）
   が当たった証拠。出なければ `TOUCH_STAGE` の文字が止まった場所を見る。
