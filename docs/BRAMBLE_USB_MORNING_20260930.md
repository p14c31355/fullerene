## 2. 今スイープで確定したこと（実測・再現あり）

- EP0 武装とゲート: precheck-2（区切り版）は 5 桁すべて 1（EP0_STATE=Setup、
  ENDPOINTS_READY=true、ARMED=true、COOLDOWN=0、失敗ステージ=0）。observe・
  fresh-gates も同旨。※precheck は 1 回目（区切り無し）が 9 パルスで一意に
  復号できず、2 回目（区切り版、10 パルス）で全桁 1 と確定。以後は区切り版を
  使用しています。
- SETUP と応答の組み立て: fresh 判定は真（2/2）。`usb/README.md` の
  「通常ランでは即 false」という記述は、いまの構成には当てはまりません。
  応答は組み立て済み（data-report の 4 桁が 1 1 1 1、2/2）。
- データ段: 退役しない。data-cmd 語のランは延べ 37（クリーン記録 28）、
  復号できた全サンプルが同じ 3 桁（退役せず / ステータス 0 / pending のまま）。
  depcmd はさらに、DEPCMD(1) の CMDACT が立ったまま（実行中）であることを
  1/1 で示しました。
- アーム: マーク入りなら返る（arm-steps 3/3 で成功、arm-land / setup-inpage でも
  結果パルス 1 = 成功）。マーク無しのアームは entry / 600 ms / 1.8 s の
  5 例すべてでコール内停止（死亡 = 最後のペット + 5.923 秒が正確に一致）。
  つまりマーク自体がドメインキープアライブを運び、計器が挙動を変えます。
- 記述子表: `DEVICE_DESCRIPTOR` は idVendor 0x1234 / idProduct 0x0001 /
  bMaxPacketSize0 64 で正しい。応答バッファの読み（response-bytes）も
  先頭 2 フィールド（bLength 18、bDescriptorType 1）が真で、後続パルスも
  VID/PID と整合（幅とフィールドの対応は暫定）。
- ホスト側の見え方: 武装構成は「即時 -71 型」、非武装は「沈黙 -110 型」に大別。
  ただし response-bytes の A/B 型は同一ビルド・同一語でも起動ごとに切り替わる。
  A: 4 パルス・3 完了・kernel.log はアドレス段のみ。
  B: 2〜3 パルス・10 完了・記述子段の -71/-110 を含む。

## 3. 今夜 棄却したもの

- 即時アーム（プルアップ直後の STARTTRANSFER）: ループが死ぬ。延期アーム設計の
  理由と同じ。
- ループへのドメインキープアライブ追加: 1.8 秒アームの停止は変わらない
  （効くのはマーク内蔵のほうで、別機構）。
- 物理 EP0 へのルーティング（ep0-physical）: 2/2 で沈黙側へ移動。
  端点番号は挙動に効くが、本筋ではない。
- 方向別 TRB（--xbl-direction-trb）: data-cmd 系 5/5 で復号不変。
- 物理 0 ルーティングを data-cmd 語に結合（fix-data-cmd）: 先行 5 サンプルと
  バイト一致。変化なし。
- no-drive のアーム窓延長（400 ms / 5 s / 10 s）: ホスト側すべて同一。打ち切り。
- SMMU / DMA の 4 表現、ABL イベント消費: ホスト側で何も動かない。
- バッファポインタのズレ: TRB と読み手が同一アドレスを参照する構図なので、
  そもそも分岐が存在しない（構成的に閉じた）。
- コマンド経路の定数・オフセット・引数順・TRB フラグ・スロット・GEVNTCOUNT 番地:
  Linux v4.19.278 と一致（差分なし）。
- 撤回 2 件: 「HWO クリア = SETUP 受信」は機械照合で成立せず（受信の証拠に
  使ってはいけない）。「遅延アームが最初のリクエストを失う」も撤回
  （どのタイミングでも同じように消費しない、の実測による）。
- consume-late のオフバンド型（ホスト沈黙のままマークが発火、1/8）:
  その後 3/3 で再発せず。稀モードとして保留。

## 9. スイープ終了後の追試（11:40〜12:05）

スイープを止めたあと、データ段が退役しない理由に絞って6本走らせました。

- 失敗の瞬間の状態（`fail-state`）: コントローラは動作中、リンクは U0、setup TRB は武装中。
- グローバルブロック（`global-block`）: GCTL はクロックゲーティング無効、GEVNTSIZ0 と GEVNTADRLO0 は読める。しかし `read(GEVNTCOUNT0)` だけが返らず、5番目のフィールドが出ませんでした。
- コマンドレジスタ（`depcmd-state`）: EP0 の DEPCMD は CMDACT クリア、状態0。setup 段のコマンドで塞がってはいませんでした。
- TRB のその後（`trb-after` / `trb-after-ep0`）: コマンドが諦めた後も、データ TRB は HWO が立ったままで TRBSTS は0。コントローラは一度も触っていません。物理1（このプロジェクトの送り先）でも物理0（Linux の送り先）でも同じです。

棄却したもの: 端点の写像（18本のルーティング済みサンプルが同じタイムアウト）、GEVNTCOUNT0 への書き込みによる確認応答、2500回の再発行を1回にした版、アーム前のソフトリセット（分類は別系統に変わったが解決せず）、arm-recover（駆動からは使えない）。

一次資料と一致していたもの: TRB の符号化（CONTROL_SETUP 2<<4、CONTROL_DATA 5<<4、HWO=bit0、LST=bit1、ISP_IMI=bit10、IOC=bit11）、`dwc3_send_gadget_ep_cmd()` の3パラメータ書き込みと CMDACT 付与と有界ポーリング。コマンド経路は差分ではありません。

結論として: コントローラはコマンドを CMDACT に受けたまま実行せず、動く段と動かない段の違いは「段そのもの」です。つまり EP0 の内部状態機械が setup から data へ進んでいません。ソフト側で唯一できないのは、完了を正規の方法で確認応答することです。`GEVNTCOUNT0` が返らないためで、台帳にはこれを3方向から記録しました。次はここから始めるのが最短です。
